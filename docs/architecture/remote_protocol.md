# `atlantis.remote/1` — Protocol Reference

**Status: descriptive reference** (Spec 0058 ruling Q8, ADR-0112 D2; Plan
0058 J13). This document describes the protocol **as the code implements
it**:
- `src/remote/src/codec.cpp`, `remote_server.cpp`, `remote_client.cpp`;
- `src/remote/src/session_file.cpp`;
- `src/connection/src/json.cpp`.

**Where they differ, the code is right.** The difference is a
documentation bug, fixed in the PR that finds it.

A change to the protocol's *behaviour* is a different thing. It needs a
Spec and a new ADR superseding
[ADR-0106](../adr/0106-attachable-runtime-transport-and-control.md), and the
version string below changes with it.

**Implementations:**
- **C++:** Atlantis Remote's client and server halves (`src/remote/`).
- **C#:** Atlantis C# SDK (`src/csharp/Atlantis.Gameplay/Remote/`).

**Conformance vectors:** `tests/csharp/conformance/codec_vectors.jsonl`,
generated by the C++ codec and staleness-checked
(`atlantis_csharp_conformance_tests`). Every implementation must decode
each `wire` value and re-encode it to the same bytes.

## 1. Discovery: the session file

A Runtime started with `atlantis_runtime --listen <port>` (`0` means
ephemeral) binds `127.0.0.1` only. Once listening, it writes one JSON
object and a `\n` to its session file:

```json
{"protocol":"atlantis.remote/1","port":51234,"token":"<32 lowercase hex>","pid":4242,"scene":"<asset GUID>"}
```

- **`window`** (optional; Spec 0064 / ADR-0126 D3): present only when the
  Runtime was started with `--parent-window <HWND>`. It is the Runtime's
  own child window's `HWND`, as a decimal integer, so the hosting process
  can size and place it. In that mode the file is written once the child
  window exists (after the first frame), not as soon as the port is bound.
- **Location:** `--session-file <path>`, else
  `./.atlantis/runtime.session.json` relative to the Runtime's working
  directory.
- **Lifetime:** the file is removed on a clean shutdown.
- **How a client finds it,** in this order:
  - an explicit path (the `atlantis` executable's `--session`);
  - else the `ATLANTIS_SESSION` environment variable, if set and non-empty;
  - else the default path above, relative to the client's working
    directory.
- **Parsing.** A client refuses a file whose `protocol` is not exactly
  `atlantis.remote/1` (`WrongProtocol`). A file is `Malformed` when any of
  these hold:
  - it is not an object;
  - `port` is not an integer in 1–65535;
  - `token` is not a string;
  - `pid` is not an integer up to 2³²−1;
  - `scene` is not a GUID;
  - `window` is present but is not an integer up to 2⁶⁴−1.

## 2. Connection

- **Transport:** TCP to `127.0.0.1:<port>`.
- **The first request must be `hello`.**
  - **Params:** `{"protocol":"atlantis.remote/1","token":"<the session token>"}`.
  - **Success:** the result is `{"protocol":"atlantis.remote/1","scene":"<asset GUID>"}`.
  - **Failure:** the server answers with `WrongProtocol` or `BadToken` and
    closes. Any other method before a successful `hello` gets
    `HelloRequired` and the connection closes. A second `hello` is a
    `BadRequest`.
- **Server side.** Each client gets its own InProcess `RuntimeConnection`
  (Spec 0054): its own subscriptions and its own failure routing by ticket.

## 3. Framing and limits

- **Lines:** each request and each response is one JSON value on one
  line, ended by `\n`. A trailing `\r` before the `\n` is ignored.
- **Request line limit:** 1 MiB (1,048,576 bytes, excluding `\n`); a longer
  request disconnects the client. Native and C# clients accept response lines
  up to 256 MiB; that is separate from the server output budget.
- **Write limit:** the server queues at most 64 MiB of output per client.
  Exceeding it disconnects the client.
- **JSON** (`json.cpp`): RFC 8259, with no comments and no trailing
  commas. Writers emit compact JSON:
  - no whitespace;
  - object members in a fixed order;
  - strings with `"`, `\`, `\b`, `\f`, `\n`, `\r`, `\t` escaped by their
    short forms and other control characters as `\u00XX` (lowercase hex);
  - all other bytes, including non-ASCII UTF-8, written as they are.

  Numbers keep their literal text through a parse.
- **The server polls after every frame** (ADR-0106 D1). Each poll:
  - reads every complete line;
  - answers every request it can answer at once;
  - parks `control.step` until its last frame completes.

## 4. Envelopes

```
request   {"id":<id>,"method":"<name>","params":{…}}      params may be omitted: {}
response  {"id":<id>,"result":<value>}
error     {"id":<id>,"error":{"code":"<name>","message":"<text>"}}
```

- **Ids** are chosen by the client and echoed unchanged. The C++ and C#
  clients use integers from 1. A line that is not a JSON object is
  answered with a `BadRequest` whose `id` is `null`.
- **Order.** Responses to a client come in the order the server produced
  them. A parked `control.step` is answered after its frames, so later
  requests may be answered first. Clients match responses by id.
- **Error codes:**
  - `BadRequest`: not a JSON object, no method, malformed or missing
    params, or an unknown method;
  - `WrongProtocol`, `BadToken`, `HelloRequired`;
  - `NoControl`: a `control.*` method on a server without a control;
  - `NoAuthoring`: an `authoring.*` method on a Runtime that serves no
    authoring session (Spec 0065), or whose scene's source cannot be found;
  - `NoAssets`: an `assets.*` query on a server without an asset provider (Spec 0081).
- **In-band results.** A method that can be refused by the World or the
  connection answers `{"ok":<value>}` or `{"err":"<error name>"}` inside
  `result`.

**Semantics** are `RuntimeConnection`'s and `RuntimeControl`'s (Specs
0052–0055):
- commands apply at the start of the Runtime's next frame, or are held
  while paused;
- a transaction is all or nothing;
- a refused command is reported by `drainFailures` under its ticket.

**The Viewport camera and the ray-cast** (Spec 0064, ADR-0128):
- `control.viewportNavigation` reads one live Runtime snapshot of the active
  scene camera before overrides, plus world-space bounds in the requested
  order. Each bound has `entity`, `kind` (`mesh` or `origin`), `min` and
  `max`. A camera-only read passes `[]`. The limit, error classification,
  and mixed-version behavior follow [ADR-0165](../adr/0165-shared-viewport-navigation-query.md).
- `control.setViewportCamera` replaces the camera the Runtime draws from,
  from its next frame; `null` restores the scene's active camera. The
  World's own camera entity is not touched. An in-process editor overlay's
  camera, when it supplies one, takes precedence. A camera the Runtime
  cannot use (for example `nearZ` of zero) is ignored for that frame.
- The camera is owned by the client that set it: when that client
  disconnects, the server clears it (ADR-0128, ruling J2).
- Hosted presentation calls use `{"ok":...}` or `{"err":{"code":...}}`. Status contains
  `sceneGeneration`, `revision`, `presented`, `owner` (None, Caller or Other) and
  `policy` (null unless Caller). A policy carries canonical `hidden` and `locked` GUID arrays
  and `isolated` (null or a nonempty confirmed keep set), at most 8,192 entries total.
  Replace atomically at the expected stamp. A null policy releases the owner's settings.
  Picks use one unit ray for Selection (nullable RayHit) or one/two for Alignment
  (the existing AlignmentFaces result). The picked stamp has already been presented.
  Refusals include Unavailable, InvalidRequest, TooLarge, NotOwner, StaleGeneration,
  StaleRevision, UnknownMember, NotPresented, NoGeometry and FaceRefused (with indexed
  alignment detail where applicable). Older hosts return their normal unknown-method
  refusal. The existing raycast, alignment and captures are unfiltered.
  See [ADR-0185](../adr/0185-hosted-viewport-presentation-policy.md).
- `control.pickAlignmentFaces` samples all requested rays in one live frame-thread dispatch. Each face contains `entity`, `mesh`, ascending cooked `triangles`, `distance`, four winding-ordered world `corners`, outward `normal` and column-major `worldMatrix`. The first refusal discards all faces. `Miss`, `UnsupportedFace`, `Ambiguous` and `TooLarge` carry `rayIndex`. `InvalidRequest`, `NoGeometry` and `Unsupported` are unindexed. See [ADR-0184](../adr/0184-shared-alignment-face-query.md).
- `control.raycast` answers the nearest Renderable the ray hits, in world
  units along a unit `direction`, or `null` for a miss. It answers
  `NoGeometry` when the Runtime keeps no pick geometry: `--listen` keeps it
  unless `--no-pick-geometry` is given.

**The Viewport overlay** (Spec 0066, ADR-0132 D2):
- `control.setViewportOverlay` replaces this client's overlay (§6.6); `null`
  clears it. The Runtime draws, from its next frame, the union of every
  client's overlay: their selections and groups, in the order the clients
  connected.
- `InvalidRequest` when the overlay is not well formed (a non-finite
  float, a colour channel outside [0, 1], a width, size or `pixelsPerUnit`
  not above zero, a nil GUID) or over one client's limits: 256 groups,
  65,536 segments, 65,536 triangles, 16,384 points and 256 selected
  entities, the totals across its groups. Nothing changes then. An
  overlay that is not one in its JSON form fails the request
  (`BadRequest`).
- The overlay is owned by the client that set it: when that client
  disconnects, the server removes it from the union.
- `control.step`'s `withOverlay` (absent is `false`): the captured image
  shows no overlay unless it is `true`, and then only the requesting
  client's own -- never another client's. The overlay the Runtime draws
  to its window is unaffected.

**Semantics** are `AuthoringConnection`'s (Spec 0065 R1–R9):
- the session is created by the Runtime at the first `authoring.*` request
  of any client; a client's authoring connection, with its subscriptions and
  failures, lives with its socket connection;
- `authoring.open` (re)reads the Runtime's scene from its source and emits
  `DocumentReopened`; until it has succeeded the queries, `authoring.apply`
  and `authoring.save` answer `NoDocument` (`authoring.document`: `null`), a
  submission is refused `NoDocument` under its ticket, and `authoring.schema`
  and the subscription methods work as usual;
- commands take effect when the request is answered: a transaction is
  applied to a copy of the document, validated (the scene schema, then the
  build's cook of its text) and kept whole or refused whole, its refusal
  reported by `authoring.drainFailures` under its ticket;
- every client's subscriptions see every client's changes;
- `authoring.apply` hands the document to the Runtime, which reloads it at
  its next frame that applies commands — while the Runtime is paused, at the
  next step or on resume, after the held commands (Spec 0065 third
  Correction); subscribers then receive `Applied` with the new
  `control.status` `sceneGeneration`. A failed reload still emits no legacy
  event; use the correlated status below for its outcome;
- `authoring.save` writes a hand-authored source atomically; an imported
  scene's save is refused.
- The additive [0112 operations](../adr/0166-guarded-authoring-save-and-reopen.md)
  observe source persistence separately from Apply. `DocumentState` carries
  `documentId`, `documentRevision`, `scene`, `source`, `provenance`,
  `lastPersistedRevision` and `dirty`. Save and Reopen compare the identity
  and revision inside host dispatch. Both can refuse with `NoDocument` or
  `StaleDocument`. Save can also refuse with `ImportedSceneNotSavable` or
  `WriteFailed`; Reopen can refuse with the same source errors as legacy Open.
  When the reply is lost, check state on the original host before
  explicitly retrying. The legacy calls retain their behavior.
- `authoring.saveAs` creates an independent source/catalog unit on an
  opted-in Windows development host. The source is relative to the assets
  root. The receipt names the copy and captured revision. Save As leaves the
  existing authoring binding and Runtime projection alone. A lost reply is
  an unknown outcome. See [Spec 0088](../specs/0088-scene-save-as.md) for names,
  refusals and recovery.

Spec 0122 recovery is additive and uses the standard retargeting guard.
`RecoveryStatus` has `capture` (`Idle`, `Writing`, `Failed` or `Unavailable`),
`protectedRevision` (a positive u64 for the current document, or null),
`copy` (null or `{id,revision,capturedUnixSeconds,pending}`) and `preview`
(null unless an exact pending copy was requested). Preview has `source`
(`Matches`, `Changed`, `Unreadable`, `AlreadySaved` or `DirtyDocument`),
`copyNodes`, nullable `sourceNodes`, `sourceLines`, `copyLines` and `truncated`.
Each excerpt has at most 20 lines and 256 Unicode scalar values per line.
The local store path and full payload are private.

A recovery receipt carries the reviewed `copyId` and `document`
(`DocumentState`). Restore advances the revision and changes the lifetime
while preserving the source and setting dirty. Discard preserves the
reviewed token. Both leave source bytes and the Apply projection alone.
Shared refusals are `NoDocument`, `Busy`, `Unavailable`, `StaleDocument`,
`StaleCopy`, `DirtyDocument`, `SourceChanged`, `SourceUnreadable`,
`InvalidCopy` and `IoFailed`. Legacy unknown method means unsupported.
Missing or malformed mutation replies leave the outcome unknown. Check
the same Runtime launch before taking another explicit action.


- `authoring.createScene` uses the same host opt-in and fixed saved-unit path
  as Save As. It writes an independent camera-only source with fresh scene
  and camera GUIDs, without reading, opening, or changing the current
  document. Host refusals are `Unavailable`, `InvalidName`, `UnsafeTarget`,
  `Busy`, `NameConflict`, `IdentityConflict`, and `WriteFailed`. An absent
  endpoint returns outer `NoAuthoring`. The exact old-host unknown-method
  refusal means unsupported. A lost or malformed reply after sending means
  unknown outcome; do not retry automatically. See
  [Spec 0089](../specs/0089-new-hand-authored-scene.md) for recovery and explicit startup.

### 5.2 Cooked asset queries (Spec 0081 / ADR-0143)

| Method | Params | Result |
|---|---|---|
| `assets.list` | `{}` | `{"ok":[<AssetSummary>…]}` in strictly increasing GUID order |
| `assets.contentMetrics` | `{"guids":["<canonical asset GUID>", ...]}` | `{"ok":{"rows":[<ContentMetricRow>, ...]}}` |
| `assets.get` | `{"guid":"<non-nil canonical asset GUID>"}` | `{"ok":<AssetDetails>}` |
| `assets.staticGroupReimportReview` | `{"mode":"begin","scene":"<Scene GUID>"}` or `{"mode":"read","id":"<review GUID>"}` or `{"mode":"cancel","id":"<review GUID>"}` | `{"ok":<StaticGroupReview>}` or a rebuild refusal |
| `assets.commitStaticGroupReimport` | `{"id":"<Ready review GUID>"}` | `{"ok":<Running RebuildJob>}` or a rebuild refusal |
| `assets.staticGroup` | `{"guid":"<non-nil canonical Scene GUID>"}` | `{"ok":<StaticGroup>}` |
| `assets.prefab` | `{"guid":"<non-nil canonical Prefab GUID>"}` | `{"ok":<StaticGroup>}` with a `name` on each node and one root, up to 64 nodes |
| `assets.prefabRevision` | `{"guid":"<non-nil canonical Prefab GUID>"}` | In-band `{prefab,revision}` or StaticGroupError from the same frozen definition |

List and get may return `{"err":"CatalogUnavailable"}`; get may also return
`{"err":"UnknownAsset"}`. Exactly one result arm is present. Invalid parameters
are outer `BadRequest`; provider absence is outer `NoAssets`. Neither initializes
the catalog. Creating/connecting a session or accessing its lazy asset endpoint
also performs no catalog query.

The executable-private `AssetHost` reads the existing cooked catalog at the first
valid query (including an unknown get), retaining a complete snapshot, empty
success, or load failure for its lifetime. All connections share it. Reconnect,
authoring open/apply and Reload view do not reload it; changed builds or a repaired
initial failure require Runtime restart. This is neither the startup catalog nor
an active-World/residency/loadability report.

```
AssetSummary {"guid":"<GUID>","type":"mesh|texture|material|scene|environment","source":"<catalog source key>"}
AssetDetails {"guid":"<GUID>","type":"<same closed type>","source":"<source key>",
              "artifactSchema":<uint32>,"sourceSchema":<uint32>|null,
              "tool":"<catalog tool>","dependencies":["<GUID>"…]}
```

Spec 0130 adds a read of a single managed glTF group in the same active
catalog. The result is `{"scene":GUID,"name":string,"nodes":[...]}`. Each
node carries exactly `parent`, `position`, `eulerRadians`, `scale` and
`renderable`. The parent is a nullable zero-based index in that array.
Each local vector is three finite Float32 values. A renderable is null or
`{"mesh":GUID,"material":GUID|null}`. A null material preserves the
scene fallback. The host returns the whole ordered group, including every
empty transform, within 63 nodes and 64 KiB.

The closed refusals are `CatalogUnavailable`, `UnknownAsset`,
`UnsupportedGroup`, `InvalidGroup` and `Unsupported`. Legacy unknown-method
replies map to `Unsupported`; successful reads leave the connection and
scene unchanged. Publishing does not change the running catalog.

**Project source inventory (0134).** `assets.scanProject` takes an empty
object. `assets.projectScanStatus` takes `{"id":"<scan GUID>"}`. The first
success contains `id`, `pending:true`, `catalogReady:false`, and empty
`roots`. Status for that exact ID returns pending or a settled reply with
independent `Inbox` and `Prefabs` roots and the active catalog's readiness.
Each root has `kind`, `coverage` (`Complete`, `Incomplete` or `Unavailable`),
`diagnostic` and `sources`. Rows contain `path`, `kind` (`Directory`, `Gltf`,
`Png`, `Prefab`, `Other`), nullable `importName`, opaque `evidence`,
`registration` (`Unknown`, `SourceOnly`, `Registered`), nullable `producer`,
`outputs` of verified asset GUIDs, and `newerPrefabSource`. Associations
require complete coverage and a ready catalog. Paths are root-relative.
Bounds are four directory levels, 2,048 combined entries, 4,096 links,
512 UTF-8 bytes per path and 2 MiB per result. Closed refusals are
`Unsupported`, `Unavailable`, `Busy` and `UnknownScan`. Earlier hosts do
not recognize the two verbs. The opt-in confers read access only. The
existing catalog verbs retain their request and reply shapes.

Spec 0120 adds optional `logicalPath` to list/get for an overridden
registered base color texture. It is a canonical full path in the Assets
`textures/` namespace, separate from the original `source` used by producers
and reimport. Older clients can ignore this member.

`assets.moveTexture` takes exactly `asset` and `expectedGeneration` as
non-nil canonical GUIDs, plus `expectedLogicalPath` and
`destinationLogicalPath` as full logical path strings. An accepted request
returns the existing running rebuild job. Poll by its ID and verify the
asset before presenting settlement. The attached catalog changes after
explicit restart into the returned generation. The distinct move refusals
are Unsupported, Unavailable, Busy, WorkspaceNeedsRepair, CatalogUnavailable,
UnknownAsset, UnsupportedProducer, InvalidPath, PathConflict, StaleSnapshot
and Unchanged. Legacy method absence maps to Unsupported. A potentially sent
request with a missing or invalid receipt requires inspection before retry.

Spec 0117 adds optional `displayName` to either item for a registered
base color texture with an override. It is the immutable active-generation
label, has the same grammar as an import name, and never replaces
`source`. The field is absent when there is no override. Updated typed
readers reject a malformed, null or duplicate present member; older
readers can continue to use the unchanged original fields.

Dependencies are sorted unique non-nil GUIDs, direct only. No artifact path,
internal AssetId or GPU state is exposed. Typed clients require all fields, known
types/errors, non-nil canonical GUIDs, strict list/dependency order and a matching
get GUID, while tolerating extra object members and future numeric schema values.
In-band errors preserve the session. Malformed/oversized/failed typed transport
sets native sticky `RemoteSession::failure()` (authoritative over the
`CatalogUnavailable` sentinel) or throws C# `RemoteException`. The CLI prioritizes
connection exit 3 over catalog exit 1. MCP forwards raw SDK responses, without
adding typed validation, retries or a session-failure requirement for raw refusals.

List-all sends one complete reply using existing limits (§3), including the shared
64 MiB pending-output budget. Overflow disconnects, never truncates or succeeds
empty. There is no pagination, streaming, new cap, event or capability handshake.

#### Static mesh preview (Spec 0091 / ADR-0151)

`assets.previewMesh` takes exactly `{"guid":"<non-nil canonical asset GUID>"}`.
Success is `{"ok":{"guid":"<same GUID>","mimeType":"image/png","width":256,"height":256,"pngBase64":"<canonical padded base64>"}}`.
There is one result arm: success or `{"err":"<PreviewError>"}`. Refusals
are `Unsupported`, `Unavailable`, `Busy`, `CatalogUnavailable`,
`UnknownAsset`, `NotMesh`, `TooLarge`, `InvalidMesh` and `RenderFailed`.
Invalid parameters are outer `BadRequest`; no preview provider returns
`Unsupported`.
Typed clients recognize only the exact older Runtime unknown-method response
as `Unsupported`. Other protocol and transport errors retain their normal
classification. Successful replies must match the requested GUID, MIME and
dimensions and have a valid PNG signature and IHDR. Encoded and decoded sizes
are checked before allocation (decoded maximum: 512 KiB).

The first admitted preview uses the same lazy catalog as list/get. The
catalog stays fixed across clients, apply and reconnect until Runtime restart.
Preview is synchronous with one shared Remote/`--exec` permit per service
interval. `Busy` does not enqueue work. No scene step, camera or authoring
change is implicit in rendering a preview. See [ADR-0151](../adr/0151-shared-offscreen-mesh-preview.md).

#### Mesh and material preview (Spec 0092 / ADR-0152)

`assets.previewMeshMaterial` takes exactly
`{"meshGuid":"<GUID>","materialGuid":"<GUID>"}` with two non-nil canonical
GUIDs. Its success arm contains both GUIDs and the same `mimeType`,
`width`, `height` and `pngBase64` fields as geometry preview. Typed clients
match both roles and reject repeated response IDs, arms and required image
members. The exact old asset unknown-method response maps to `Unsupported`.

The refusal tokens are `Unsupported`, `Unavailable`, `Busy`,
`CatalogUnavailable`, `UnknownMesh`, `UnknownMaterial`, `NotMesh`,
`NotMaterial`, `InvalidMesh`, `InvalidMaterial`, `UnsupportedMaterial`,
`DependencyUnavailable`, `IncompatiblePair`, `TooLarge` and
`RenderFailed`. Invalid parameters are outer `BadRequest`.

Both preview methods share the retained catalog and one Remote/`--exec`
permit. The current recipe supports opaque `PbrDirectLit` with one sRGB
RGBA8 base texture and zero emissive contribution. The texture must match
the material's direct dependency in that snapshot. See [Spec 0092](../specs/0092-mesh-material-preview.md)
for input bounds and lifetime rules.

### 5.2.1 Managed asset rebuild (Spec 0085 / ADR-0146)

| Method | Parameters | Result |
|---|---|---|
| `assets.rebuild` | `{"asset":"<AssetGuid>"}` | `{"ok":<Job>}` with `Running`, or `{"err":"<StartRefusal>"}` |
| `assets.rebuildStatus` | `{}` for latest, or `{"jobId":"<RebuildId>"}` | `{"ok":{"activeGeneration":<GenerationId or null>,"job":<Job or null>}}`, or `{"err":"<StatusRefusal>"}` |

The two ID domains use canonical non-nil GUID strings. A job carries
`id`, `asset` and `state`. `Succeeded` adds `generation`. `Failed` adds
`failure` with `stage`, `code`, `diagnostic` and an optional unsigned
32-bit `exitCode`. See [Spec 0085](../specs/0085-shared-asset-rebuild.md)
for the closed alternatives, timeout, retention and workspace recovery.

An opted-in Runtime can publish a generation while remaining on its
original catalog. A local restart selects the published generation.
Neither status nor discovery changes which catalog is active. For the
new methods only, typed clients recognize the pinned legacy
`BadRequest` / `unknown or malformed asset query` as client-local
`Unsupported` and keep the shared session usable. Unexpected responses
follow existing protocol-error handling.

[Spec 0116](../specs/0116-registered-texture-reimport.md) and
[ADR-0167](../adr/0167-managed-texture-source-replacement.md) admit one
registered base color texture in an active named managed generation through
the same rebuild call. The host resolves the GUID and takes the replacement
from the original project inbox path; the wire never receives a path or PNG.
Publication retains the asset GUID and bindings. A clean input refusal can be
retried through rebuild after correction. An unverified exchange or publication
leaves the workspace held for repair: the existing failure diagnostic describes
the hold and starts are refused with `WorkspaceNeedsRepair`. Clients can query
direct material references with the existing catalog list and details calls.
No new request, result field or error token is introduced.

For local recovery, retain the project's `.pending/<job-id>/replacement.json`
and any `previous` backup or `replace/texture_<name>` unit under that job.
The record names the texture, expected generation and old/new SHA-256 values.
Stop writers and inspect those units and the expected complete generation
before clearing either dirty marker. Verify the frozen evidence and sealed
registry before preserving the new version or restoring the backup.
A missing or ambiguous recovery record does not authorize either action.

#### Display rename (Spec 0117 / ADR-0168)

`assets.checkTextureRemoval` accepts `{asset,expectedGeneration}` and starts
the bounded reference check for one registered base color texture.
`assets.textureRemovalCheckStatus` accepts `{checkId}`. An OK result for
either has `{id,asset,expectedGeneration,state,blockers,truncated,incomplete,diagnostic}`.
State is Checking, Ready, Referenced, CheckIncomplete or StaleCheck.
Blockers contain `{asset,source,slot}`, with a logical source and either null
or BaseColor, Normal, MetallicRoughness, Occlusion or Emissive for the slot.
There are at most 16 blockers. Truncation and incomplete coverage are independent.

`assets.removeTexture` accepts `{asset,expectedGeneration,checkId}` and consumes
the matching Ready check on admission. It returns a Running rebuild job.
Observe its settlement through `assets.rebuildStatus`. A successful publication
requires explicit restart into the returned generation. It keeps the original
inbox PNG. No preview, document or running catalog is mutated in place.
All identifiers are non-nil canonical GUID strings. The shared in-band
refusals are Unsupported, Unavailable, Busy, WorkspaceNeedsRepair, CatalogUnavailable,
UnknownAsset, UnsupportedProducer, StaleCheck and UnknownCheck. A legacy unknown
asset method maps to Unsupported. Never silently retry a possibly sent confirmation.

`assets.renameTexture` accepts exactly
`{"asset":"<AssetGuid>","expectedGeneration":"<GenerationId>","displayName":"new_label"}`.
It admits the same Running Job as rebuild; settle the returned ID through
`assets.rebuildStatus`. A known expired or unavailable query does not
prove a failed write. Treat loss or invalidity of a possibly sent start's
receipt as unknown, retain the identity and proposal, and verify settlement
before retrying. The exact legacy unknown-method refusal maps to Unsupported.

Start refusals are `Unsupported`, `Unavailable`, `Busy`,
`WorkspaceNeedsRepair`, `CatalogUnavailable`, `UnknownAsset`,
`UnsupportedProducer`, `InvalidName`, `NameConflict`, `StaleSnapshot`
and `Unchanged`. Only a matching active named managed generation can rename
one registered sRGB color PNG. Publication keeps the texture GUID, logical
source, registered files, original inbox and bindings. Clients see the new
name after an explicit restart into the published generation. The host
stores overrides in `texture-display-names.json` and freezes them at
`textureDisplayNames` in manifest v8. An older Runtime cannot activate v8;
use only updated writers on a workspace with overrides. Older snapshots
whose map differs from the committed map stay readable but cannot write.

If rename publication is unverified, the dirty markers hold managed writes.
Use the owned `.pending/<job-id>/rename.json` record and exact previous and
requested map bytes, under the offline settlement rules in
[ADR-0168](../adr/0168-generation-scoped-asset-display-names.md). Querying
discovery never reads or alters this mutable recovery state.

### 5.2.2 Managed materials (Spec 0094 / ADR-0153)

| Method | Parameters | Success |
|---|---|---|
| `assets.materialRead` | `{material}` | `{material,recipe,editable,activeGeneration}` |
| `assets.materialSave` | One of the four exact request arms below | A job in state `Running` |
| `assets.materialStatus` | `{}` or `{jobId}` | `{activeGeneration,workspaceNeedsRepair,job?}` |
| `assets.previewMaterialDraft` | `{mesh,recipe}` | `{mesh,recipe,mimeType,width,height,pngBase64}` |

All success payloads are in `{"ok":...}`; typed refusals use
`{"err":"<MaterialError>"}`. All IDs are canonical non-nil asset GUID
strings. Active generation is explicitly nullable for a seed. A recipe is
`{values,filter,address}` where `values` is `{texture,color,metallic,roughness}`,
`color` is three linear RGB float32 values, and all five numeric fields are
finite and in [0,1]. The sampler tokens are `Nearest` / `Linear` and
`Repeat` / `ClampToEdge`.

| Mode | Members in addition to `mode` |
|---|---|
| `Create` | `name,values` |
| `Copy` | `name,material,values` |
| `Edit` | `material,activeGeneration,expected,values`; `expected` is the original editable values |
| `Resume` | `material` |

A job contains `jobId`, `state`, `mode`, and the requested name and/or
material GUID as appropriate for that mode. `Succeeded` adds
`savedMaterial` and `generation`. `Failed` adds `failure` with `stage`,
`code`, a diagnostic of at most 4096 UTF-8 bytes, optional unsigned
32-bit `exitCode`, and `sourceState`. Only `Committed` adds
`savedMaterial` to the failure. `Unknown` requires workspace inspection
before another mutation. The other source state is `NotCommitted`.
One active and the last 16 terminal material receipts are retained in
memory. `UnknownJob` for an explicit ID does not determine its outcome.
A lost or invalid admission receipt is an unknown outcome. The latest
job is a diagnostic hint; verify the durable target and settle the
previous request before retrying. Nothing is retried automatically.

Bad request shapes are outer `BadRequest`; only the exact legacy
`BadRequest` / `unknown or malformed asset query` refusal maps to
`Unsupported` for well-formed requests. Save and Status without a
trusted project profile return `Unavailable`. Draft preview uses the
same bounded PNG and admission slot as the other previews, and has no
persistent material GUID or write side effect. A successful publication
does not change the active generation. See
[Spec 0094](../specs/0094-basic-material-authoring.md) and
[ADR-0153](../adr/0153-managed-material-authoring-and-draft-preview.md).

### 5.3 Correlated authoring apply (Spec 0083 / ADR-0144)

| Method | Params | Result |
|---|---|---|
| `authoring.applyTracked` | `{}` | `{"ok":<Receipt>}` or `{"err":"<ApplyError>"}` |
| `authoring.applyStatus` | `{}` or `{"id":null}` or `{"id":"<ApplyId>"}` | `{"ok":<Snapshot>}` or `{"err":"UnknownApply"}` for an unavailable explicit id |

```
Receipt  {"id":"<ApplyId>","documentRevision":<uint64>}
Snapshot {"currentDocumentRevision":<uint64>|null,"request":<Record>|null,
          "projection":{"receipt":<Receipt>,"generation":<uint64>}|null}
Record   {"receipt":<Receipt>,"state":"Pending"}
       | {"receipt":<Receipt>,"state":"Applied","generation":<uint64>}
       | {"receipt":<Receipt>,"state":"Failed","error":"<ReloadError>"}
       | {"receipt":<Receipt>,"state":"Superseded","supersededBy":"<ApplyId>"}
```

IDs are opaque non-nil canonical GUID strings. Revisions and generations in
receipts/outcomes are positive. Reload errors are `ScenePreparationFailed`,
`RenderPreparationFailed`, or `RuntimeStopped`. Invalid ids are outer
`BadRequest`; absence of the provider is `NoAuthoring`. An old Runtime may
return `BadRequest` for the new methods; typed clients treat that as a protocol
failure. They do not fall back to a mutating legacy call.

Acceptance captures the document at that revision. Revisions advance on
successful open or nonempty accepted transactions; save and apply do not
advance them. The newest acceptance replaces any pending snapshot immediately,
including during pause; rejection leaves the earlier snapshot pending. Applied
is queryable before the legacy event is delivered. Failure leaves the accepted
document intact; a recoverable failure keeps the existing World and generation.
Neither a save nor a reopen is a Runtime swap.

Status is non-destructive and shared across clients. Without an id it observes
the newest accepted request. Explicit lookup works for the pending request,
64 most recent terminal records, and the last successful projection even after
its record is evicted. Reconnection to the same Runtime preserves those
records; restart does not. An unavailable id or lost reply gives no proof of
failure or success. Do not infer ownership from the newest record or retry blindly.

## 6. Values

### 6.1 Scalars and identifiers

- **Floats:** a float is a JSON number, written as C++ `std::to_chars`
  writes a `float`.
  - **Shortest round trip:** the shorter of fixed and scientific notation,
    fixed on a tie. An integral value in fixed notation is written as its
    exact integer, which is no longer than its shortest digits padded with
    zeros and closer (`5409459712`, not `5409459700`).
  - **Scientific notation:** a lowercase `e`, an explicit sign and at
    least two exponent digits, e.g. `1e+20`, `1e-05`, `-0`, `0.1`,
    `3.4028235e+38`.
  - **Non-finite:** NaN, +∞ and −∞ are the strings `"nan"`, `"inf"` and
    `"-inf"`, so the World's `NonFiniteValue` refusal stays reachable.
  - **Reading:** a reader accepts any JSON number that converts to a
    finite float without range error.
- **`u64` property values** are **decimal strings** (`{"u64":"18446744073709551615"}`).
  Tickets, subscription ids, frame numbers, counts and sequence numbers
  are plain JSON integers.
- **TypeId and FieldId:** `"0x"` followed by exactly 16 lowercase hex
  digits.
- **GUIDs** (entity and asset): lowercase RFC 9562 text,
  `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx`; the nil GUID is all zeros.

### 6.2 PropertyValue

A one-member object tagged by the alternative:

```
{"u64":"<decimal>"}  {"f32":<float>}  {"vec3":[<float>,<float>,<float>]}  {"vec4":[…4…]}
{"assetGuid":"<GUID>"}  {"entityGuid":"<GUID>"}  {"enum":<int64>}  {"absent":true}
```

### 6.3 Address, commands and events

```
Address  {"entity":<E>,"component":<T>,"field":<FieldId>}
Command  {"kind":"CreateEntity","entity":<E>}       {"kind":"DestroyEntity","entity":<E>}
         {"kind":"AddComponent","entity":<E>,"component":<T>}
         {"kind":"RemoveComponent","entity":<E>,"component":<T>}
         {"kind":"SetProperty","address":<Address>,"value":<V>}
Event    the same shapes with kinds EntityCreated, EntityDestroyed, ComponentAdded,
         ComponentRemoved, PropertyChanged (the last carries the applied value)
```

### 6.4 Failures, tickets, filters

```
Failure  {"ticket":<n>,"error":"<AccessError>"}
Ticket   {"first":<n>,"count":<n>}       (a transaction; count 0 for an empty one)
Filter   {"kinds":["EntityCreated",…],"entity":<E>|null,"component":<T>|null}
```

- **`kinds`:** listed in the order EntityCreated, EntityDestroyed,
  ComponentAdded, ComponentRemoved, PropertyChanged.
- **Matching:** an event matches when its kind is listed, and its
  entity/component equal the filter's when those are not `null`.

### 6.5 Error names

- **`AccessError`:** `UnknownEntity`, `NilGuid`, `DuplicateGuid`,
  `UnknownComponentType`, `ComponentMissing`, `ComponentAlreadyPresent`,
  `UnknownField`, `FieldNotEditable`, `KindMismatch`, `EnumValueOutOfRange`,
  `NonFiniteValue`, `LightLimitExceeded`, `ActiveCameraProtected`.
- **`ConnectionError`:** `UnknownSubscription`.
- **`ControlError`:** `InvalidRequest`, `NotRendering`, `CaptureFailed`,
  `Stopped`, `NoGeometry`.

### 6.6 Control values

```
FrameReport  {"frame":<n>,"applied":bool,"data":<FrameData>,"image":null|{"path":"…","width":<n>,"height":<n>}}
FrameData    {"directionalLights":[{"direction":[3],"color":[3],"intensity":<float>}…],
              "pointLights":[{"position":[3],"color":[3],"intensity":<float>,"range":<float>}…],
              "view":[16],"projection":[16],"drawItemCount":<n>,"exposureCompensationEv"?:<float>}
Diagnostics  entries [{"sequence":<n>,"severity":"warning"|"error"|"fatal","message":"…"}]
ViewportCamera {"worldMatrix":[16],"fovYRadians":<float>,"nearZ":<float>,"farZ":<float>}   (column-major)
Ray          {"origin":[3],"direction":[3]}                                        (world space, unit direction)
RayHit       {"entity":"<E>","distance":<float>}
```

When available, `exposureCompensationEv` is the finite numeric compensation
used by the active camera's output transform, including when the viewport
override supplies pose and lens. Omission means unavailable, commonly on
older Runtime builds. A reported zero is an exposure value. See
[ADR-0180](../adr/0180-shared-frame-report-exposure.md).

**The Viewport overlay** (Spec 0066, ADR-0132 D1). Its floats are JSON
numbers only (no `"nan"`/`"inf"` text: an overlay's floats are finite).
Every member is required.

```
ViewportOverlay {"selection":["<E>"…],"groups":[<Group>…]}
Group     {"anchor":null|{"position":[3],"pixelsPerUnit":<float>},
           "segments":[{"a":[3],"b":[3],"color":[4],"depth":<Depth>,"width":<float>}…],
           "triangles":[{"a":[3],"b":[3],"c":[3],"color":[4],"depth":<Depth>}…],
           "points":[{"p":[3],"color":[4],"depth":<Depth>,"size":<float>}…]}
Depth     "Tested" | "OnTop"
```

- **`selection`:** the entities the Runtime outlines, from their meshes.
- **A group** is world (`anchor` `null`: its positions are world
  positions) or screen-constant: its positions are offsets from the
  anchor's `position`, one unit drawn as `pixelsPerUnit` pixels at the
  anchor's view depth, from the frame's own camera.
- **`color`:** straight alpha, authored in sRGB, each channel in [0, 1].
- **`width`** (a segment's) and **`size`** (a point's) are in pixels.
- **`depth`:** `Tested` against the scene's depth, or drawn `OnTop` of it.

### 6.7 The schema

`connection.schema` returns an array of types:

```
{"id":<T>,"name":"world::Light","kind":"Struct"|"Enum","version":<n>,
 "fields":[{"id":<FieldId>,"name":"intensity","kind":"Primitive"|"Struct"|"Enum",
            "primitive":"UInt64"|"Float32"|"Vec3Float32"|"Vec4Float32"|"AssetGuid"|"EntityGuid",
            "type":<T>,"flags":<n>,"offset":<n>}…],
 "constants":[{"name":"Directional","value":<int64>}…]}
```

- **`flags`:** a bit set — Serializable 1, Editable 2, AssetReference 4,
  EntityReference 8, Optional 16.
- **`primitive`:** meaningful only for `Primitive` fields (other fields
  carry `UInt64`).
- **`type`:** `0x0000000000000000` for primitives.
- **`offset`:** the field's byte offset in World's C++ struct. It is
  transmitted, but it is **internal layout (ADR-0034)**: clients ignore it,
  and the Gameplay SDKs never use it.

In `authoring.schema`, Spec 0084 optionally appends `targetAssetType` to a
primitive AssetGuid field marked AssetReference. Its value is the exact
lowercase cooked catalog type token from §5.2. The server omits it when
unspecified. Typed clients reject a present invalid token or an annotation on
an ineligible field as malformed schema. Old readers ignore this additional
member. It is advisory selection metadata and is outside the persisted
semantic scene hash.

  kind is listed and its node and component equal the filter's when those
  are not `null`; `ActiveCameraChanged`, `DocumentReopened` and `Applied`
  carry no node, and only `PropertyChanged`, `ComponentAdded` and
  `ComponentRemoved` carry a component. Either participant can match the
  node filter for `NodeOrderChanged`. Only the moved node matches the
  node filter for `NodeMovedInSiblingOrder`.
- **Error names:**
  - **`AuthoringError`:** `NoDocument`, `UnknownNode`,
    `UnknownComponentType`, `ComponentMissing`, `ComponentAlreadyPresent`,
    `ComponentRequired`, `UnknownField`, `KindMismatch`,
    `EnumValueOutOfRange`, `NodePositionOutOfRange`, `FieldOutOfDomain`,
    `NonEmptyDocument`, `NodeGuidNonNil`, `NodeGuidUnique`, `ParentExists`,
    `ParentAcyclic`, `ActiveCameraExists`, `ActiveCameraHasCamera`,
    `ComponentExclusivity`, `LightRangeMatchesKind`, `MaxDirectionalLights`,
    `MaxPointLights`, `CookRefused`, `NotRepresentableInSource`, `InvalidNodeName`,
    `SiblingOrderStaleRevision`, `SiblingOrderRequiresHandAuthored`, `InvalidSiblingSwap`,
    `InvalidSiblingMove`, `InvalidGuardedPropertyBatch`, `PropertyBatchStaleRevision`,
    `InvalidGuardedDuplicateBatch`, `DuplicateBatchStaleRevision`,
    `InvalidGuardedNameBatch`, `NameBatchStaleDocument`;
  - **`OpenError`:** `SourceUnreadable`, `SourceParseFailed`,
    `SourceInvalid`;
  - **`SaveError`:** `NoDocument`, `ImportedSceneNotSavable`, `WriteFailed`;
  - **`ApplyError`:** `NoDocument`, `NoSceneSink`, `CookFailed`,
    `DecodeFailed`, `ReloadRefused`.

Spec 0069 / ADR-0142 adds authoring labels: empty means unnamed; duplicates are
valid and identity remains the GUID. Names are valid UTF-8 up to 255 bytes,
excluding U+0000–001F, U+007F–009F and U+2028/U+2029, without normalization.
`SetNodeName` retains transaction/ticket/refusal semantics and emits one event
per successful command, even for an unchanged name. The event has a node and no
component. A missing legacy summary name decodes as empty; a present invalid
name is refused. Old summary decoders tolerate the extra member, but rename
commands/events require updated peers, including all-events subscribers.
No RPC method or protocol version changes. CLI uses
`scene name <node-guid> <json-string>` (also in `scene tx`; `""` clears), and MCP
uses its existing `authoring.submit_transaction` tool with the command above.

Spec 0104 / ADR-0160 exchanges two global slots for adjacent siblings under
the same parent, including root nodes. Submit it as the only command in a
transaction and drain that ticket's failures. Its one event names the
resulting zero-based positions and document revision. Request
`NodeOrderChanged` explicitly in an unfiltered all-kinds subscription to
establish support. A legacy Runtime returns `BadRequest` with message
`malformed or missing filter`. In that case clients retry once with the
original kinds and retain the connection for ordinary commands. Use
`authoring.listNodes` to inspect the current order after uncertain settlement.

Spec 0105 / ADR-0161 inserts a node before or after an anchor under the
same parent, including the scene root. Use a single-command transaction
with the observed document revision. The operation rotates the affected
sibling slots and reports one event with the moved node's old and new
zero-based global positions and the new revision. Existing gaps and mixed
transactions are refused.

Probe support with the unfiltered all-kinds subscription that includes
`NodeMovedInSiblingOrder`. On a correlated `BadRequest` with the exact
message `malformed or missing filter` and no result, retry with the 0104
unfiltered all-kinds set, then with the original set if that retry receives
the same refusal. A valid nonzero subscription confirms its tier. Submit
the relative operation only after the 0105 tier is confirmed. Existing
subscribers retain their event sets, and a fresh `authoring.listNodes`
shows the current order. If a move reply is lost or invalid, inspect the
current order and revision before another move. Apply remains separate.

Spec 0106 / ADR-0162 adds the optional boolean
`supportsGuardedPropertyTransactions` to `Document`. A literal true
on the current open document enables guarded property writes.
Older readers can read the descriptor's existing members. Other
capability values leave the guarded path unavailable.

Place `RequireDocumentRevision` first in `authoring.submitTransaction`
with one to 64 `SetProperty` commands to the same component and field
on distinct nodes. The guard consumes a ticket and emits no event.
The host checks shape and revision at admission. The two guard
refusals use the first guard's ticket. Success consumes one document
revision and publishes ordinary property events in write order.
Drain the matching failures before Apply. Older hosts refuse the
unknown command while decoding the whole request. Keep the guarded
writes together and inspect the document before retrying if settlement
is unknown.

### Guarded Transform transactions

[ADR-0163](../adr/0163-guarded-transform-batches.md) adds the optional
`supportsGuardedTransformTransactions` member to the open document.
Only literal true enables this command. It is independent of the
guarded single-property capability.

`RequireTransformBatchRevision` carries an unsigned
`expectedRevision` and goes first in the existing transaction.
The following 1–192 writes address distinct whole-vector Transform

emits no event. Shape and revision use the existing guarded refusal

### Guarded subtree duplication transactions

[ADR-0164](../adr/0164-guarded-duplicate-transactions.md) adds the optional
`supportsGuardedDuplicateTransactions` member to the open document.

Spec 0132 uses that guard for Prefab instantiation. An append can specify
`{"kind":"SetPrefabOrigin","node":<EntityGuid>,"prefab":<AssetGuid>}` once on
a newly created root. The host verifies the Prefab in the current saved
build. Node summaries and `NodeCreated` optionally include `prefabOrigin`.
The document optionally advertises `supportsPrefabOrigin` and
`supportsPrefabRegistration`. Omitted capabilities are unavailable.

`authoring.createPrefab` requires separate checkout write permission and
refuses a mismatched document token with `StaleDocument` and an ineligible
subtree with `UnsupportedSubtree`. After a missing or invalid receipt, check
both files in the canonical registration unit and confirm the request has
settled before retrying. The registration does not modify the document.
An explicit Saved Scenes Build/Open makes the Prefab visible in a new
snapshot. List/get rows optionally include `isPrefab: true` and retain
`type: "scene"` for existing clients.
Only literal true enables the new guard. Discovery is independent of
the earlier guards and is scoped to the current open document.

Spec 0133 retains the three-field Prefab tree reply. Revision reads return
the SHA-256 of the verified frozen source and only succeed for a valid tree.
Source update requires checkout write permission and compares the requested
revision with both the active definition and the current canonical source.
The write and the next explicit 0090 Build/Open have separate outcomes.

A Prefab structural receipt settles one guarded transaction. Its before
and after values contain canonical bounded subtree source, outside
`parent` (GUID or null), sorted document `slots` and a SHA-256 `order`
guard. Each subtree is at most 64 nodes and 64 KiB. The empty state has
empty source and slots with a null parent. The receipt moves the document
revision by one on a change and preserves it for an already current
instance. Apply is separate. Replay checks both the current document token
and the expected subtree and order. Clients should use the received
before/after values to replay history.

Updated clients discover transaction support with optional
`supportsPrefabSync` in document information. An individual node summary
can carry a lowercase 64-hex `prefabBaseline` alongside `prefabOrigin`.
Legacy listeners continue to receive the existing structural and component
event kinds. After a lost mutation result, clients inspect the target and
wait for settlement before retrying.

Put `RequireDuplicateBatchRevision` with unsigned `expectedRevision`
first in `authoring.submitTransaction`. The payload either appends
1–64 distinct explicit GUIDs and initializes only those copies, or
destroys exactly the current suffix of 1–64 distinct nodes. Shape and
revision refusals use the guard ticket and the corresponding
`InvalidGuardedDuplicateBatch` or `DuplicateBatchStaleRevision` error.
Success has one document revision and emits ordinary authored events.
The guard takes one ticket and emits no event. Drain matching failures
before requesting Apply. Older peers keep their existing commands,
and an older host refuses this guard during transaction decoding.

### Guarded name transactions

[ADR-0189](../adr/0189-document-guarded-node-name-batch.md) adds the optional
`supportsGuardedNameTransactions` boolean to the open hand-authored document.
Only literal true enables this transaction on the current open document.

`RequireNameBatchDocument` goes first in `authoring.submitTransaction`.
Its only payload member is `expectedDocument`, with exactly the existing
canonical `documentId` and positive unsigned `documentRevision`. The
following 1–64 commands are ordinary `SetNodeName` for distinct non-nil
nodes. The guard consumes its own ticket and emits no event.
`InvalidGuardedNameBatch` settles an invalid shape or unsupported source.
`NameBatchStaleDocument` settles a token mismatch. Both identify the guard
ticket. A successful batch advances one revision and emits existing
`NodeNameChanged` events in write order. Drain matching failures before
requesting Apply. An older host refuses the unknown guard during decoding
and guarded clients do not send unguarded replacement writes.

### Guarded render-look writes

[ADR-0191](../adr/0191-render-look-preview-and-adoption.md) adds the optional
`supportsGuardedRenderLookTransactions` boolean to a hand-authored document.
A client uses the guard only when the flag is true.

`RequireRenderLookDocument` must lead an `authoring.submitTransaction` of one
to 203 distinct `SetProperty` commands. The guard has exactly four payload
members: `expectedDocument` (the existing document token), `activeCamera`
(the camera node GUID), `lightRoster` (up to 65 light node GUIDs in ascending
canonical order), and `placementSignature` (a nonempty string of at most
128 KiB). The host checks the open document, token, active camera, full
direct-light roster and target placement.

The placement signature is the concatenation of target and ancestor rows in
ascending node GUID order. A row is `node/parent/role` followed by slash-separated
unsigned decimal binary32 bit patterns and a terminal `|`. An empty parent
means root. Roles are `C` for the active camera, `D` for the directional light,
`P` for a point light, and `T` for an ancestor outside the target roster.
The bit patterns are local position, local scale, and local Euler angles
(XYZ order for each), omitting Euler angles for the directional light. A camera row
ends with vertical FOV in radians, near plane, and far plane. A directional light
must be a leaf. Scene values that the look can edit are excluded from the basis.

Writes are limited to the active camera's exposure, five Fog and two Bloom
leaves, light color and intensity, point range and directional local Euler
rotation. The guard consumes one ticket without emitting an event. Shape,
token and target failures are reported as `InvalidGuardedRenderLook`,
`RenderLookStaleDocument` and `RenderLookTargetChanged`, respectively. A
refusal changes no field. Settle the ticket range and verify writes before
requesting Apply. Existing guards and unguarded edits keep their behavior.

### Render look capture

`control.status` optionally advertises `supportsRenderLookCapture: true`.
With that capability, `control.captureRenderLook` accepts a `guard` in the
`RequireRenderLookDocument` wire shape, the settled `applyId` and
`generation`, one `camera` in the existing viewport camera shape, two
ordered arrays of complete `SetProperty` values in `looks`, and an
ordered `outputs` array of two fresh caller-owned absolute PNG paths.
The Runtime checks both variants against the same projection and returns
`err` on a refusal or failure. It does not issue a step or Apply.

Success returns `document`, `applyId`, `generation`, `activeCamera`, and
`variants` in A, B order. Each variant has `role`, `values` and `capture`.
The capture uses the FrameReport image and data fields with a zero frame and
`applied: false` to identify offscreen work. Both images are 960 × 540.
Clients validate the values, identities and output paths against their request.

The CLI's `runtime capture-look <manifest>` reads a bounded text manifest.
It contains a `require-render-look-document` row as in a scene transaction,
a `projection <apply-id> <generation>` row, and a `camera` row followed by
the 16 column-major world-matrix scalars, vertical FOV, near plane and far
plane. Each variant is an `output <absolute-path>` row followed by the
complete set of ordinary `scene set` rows in that variant. List A first.

### Managed asset import

[Spec 0086](../specs/0086-new-asset-import.md#requirements) defines

They use the existing typed `ok`/`err` envelopes. The start receipt echoes

### `control.pickMaterialBinding`

One bounded read of the nearest unique material binding in an existing Runtime
projection (Spec 0138 and ADR-0186). Parameters have required `ray`,
`minDistance`, `maxDistance`, and `sceneGeneration`; optional `viewport` is
the existing `{sceneGeneration, revision}` stamp. The ray uses finite numeric
triples and the existing unit-length tolerance. The distances are finite,
with `0 <= minDistance < maxDistance`; the query includes both endpoints.
A supplied viewport must match the requested scene generation, have been
presented, and have no active visibility policy.

Success is `{"ok":{"sceneGeneration":G,"entity":E,"mesh":M,"material":A,"distance":T,"slot":"Renderable.materialAsset"}}`
with the matching `viewport` only when supplied. GUIDs are canonical and
non-nil. Refusals are `{"err":"Code"}`, where Code is `InvalidRequest`,
`Unavailable`, `Unsupported`, `StaleGeneration`, `StaleViewport`,
`NotPresented`, `ActivePolicy`, `NoGeometry`, `Miss`, `Ambiguous`,
`UnsupportedBinding`, or `TooLarge`. Prior hosts refuse the unknown method.
The ordinary raycast and hosted selection pick shapes are unchanged.

### Registered static glTF reimport (0139)

The same named Runtime generation supplies the original keyed glTF and
the catalog used by the review. Begin returns a `Pending` receipt, with
`id`, `scene`, `generation` (all non-nil canonical GUIDs), `name`,
`state`, `diagnostic` and `rows`. Read returns the retained receipt.
Cancel changes it to `Expired` with no publication. Other states are
`Ready`, `Blocked` and `Failed`. An unretained or already consumed ID
returns `UnknownJob`. The complete payload is limited to 64 KiB.

A row contains `key`, `guid`, `change`, `before`, `after`, and
`diagnostic`. Change is `Matched`, `Added`, `Removed`, or `Conflict`.
A revision is null or an object containing `label`, zero-based `index`,
nullable zero-based `slot` and nullable material GUID `material`. Null
material on a mesh slot represents no explicit material. Only a
complete `Ready` review can be confirmed. The one-use confirmation is
settled via `assets.rebuildStatus` using the returned job ID. A lost
confirmation receipt is an unknown outcome. Check settlement before
trying again. Publication uses the existing explicit activation flow.
Earlier hosts refuse the methods as unsupported.


### Cooked content metrics (0140)

This request uses the catalog snapshot established by the normal asset
queries. It takes 1–32 distinct canonical GUIDs in a single guids array.
Each result row has guid and exactly one of mesh, texture or err, in
request order. A mesh carries artifactSchema (4 or 5) and indexedTriangles.
A texture carries artifactSchema (3), width, height, layout (Rgba8 or Bc7),
mipCount and pixelPayloadBytes. The latter is the stored mip-chain payload
size. The service validates header layout and file length, without reading
the payload or reporting GPU allocations. A per-row err is UnknownAsset,
UnsupportedAssetType, UnsupportedArtifactSchema, UnreadableArtifact or
InvalidArtifact. CatalogUnavailable is a whole-request refusal. A malformed
request is BadRequest. Older hosts refuse the new method as Unsupported
through the clients' existing unknown-method mapping. The bounded reply
contains no paths, scene edits, frame samples or capture requests.
