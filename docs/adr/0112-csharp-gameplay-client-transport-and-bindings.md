# ADR 0112: C# Gameplay Client — Transport, Bindings and Module

- **Status:** Proposed
- **Date:** 2026-10-09
- **Deciders:** slmao
- **Acceptance:** pending (review of Spec 0058's own branch PR, [PR #238](https://github.com/slmao/Atlantis/pull/238))
- **Related Spec:** [Spec 0058: C# Gameplay](../specs/0058-csharp-gameplay.md) (`In Review`)
- **Related ADR(s):**
  - It speaks [ADR-0106](0106-attachable-runtime-transport-and-control.md)'s
    `atlantis.remote/1` unchanged, and turns it into a cross-language
    contract (D2).
  - It extends [ADR-0111](0111-schema-generated-typed-bindings.md)'s
    generation (committed output, `eol=lf`, staleness tests, the naming
    rule) to a C# target. The C++ output is unchanged.
  - It carries [ADR-0110](0110-gameplay-sdk-client-library-and-execution-model.md)'s
    model to C#: client-driven logic, the frame boundary as the only time,
    no custom components.
  - It pairs with [ADR-0113](0113-dotnet-toolchain-and-build-integration.md)
    (the toolchain).

## Context

- **The maintainer** (2026-10-09):
  - one schema, two calling styles (reflective for the editor and agents,
    typed for gameplay);
  - the generator gains a C# backend, with `world.Get<Transform>(entity)`;
  - the C# client is an ordinary out-of-process client;
  - v1 may not meet "no IPC/Variant/Reflection on the gameplay hot path",
    and says so; hot-path work is named only;
  - managed hosting inside the Runtime, NuGet, Android C# and C# editor
    extensions are excluded.
- **Two ways to reach the Runtime from C#:**
  - implement `atlantis.remote/1` in C#;
  - call the native C++ SDK through P/Invoke, which still reaches the
    Runtime over the same protocol, via `RemoteSession`.

  Both cross the same process boundary. Each call waits for a frame
  boundary (about 33 ms measured on the default scene); TCP, JSON and
  marshaling are microseconds beside it.
- **The protocol's only definition today** is Remote's private
  `codec.h` comment and code. It has one implementation.
- **Naming.** Schema names are camelCase fields under module-prefixed types
  (`world::Light.intensity`). C# convention is PascalCase.
- **`System.Guid`'s byte layout** is mixed-endian; its text form is RFC
  9562, which is what the wire carries.

## Decision

1. **Transport: managed C# speaking `atlantis.remote/1` directly**
   (Spec 0058 Q1, (a)).
   - **What the C# library implements:**
     - the session file;
     - the TCP socket;
     - JSON-lines framing;
     - `hello`, with request ids and pipelining;
     - the value codec (`System.Text.Json`, in-box).
   - **No native engine code is loaded.** There is no C ABI and no P/Invoke
     of engine code.
   - The engine links nothing of it.
2. **The protocol becomes a cross-language contract** (Q8, P-a).
   - **A reference document,** `docs/architecture/remote_protocol.md`,
     describes `atlantis.remote/1` as it is:
     - framing and limits;
     - the session file and `hello`;
     - every method's params and result;
     - the value encoding;
     - the error names.
   - **Conformance vectors,** generated by the C++ codec and committed, are
     decoded and re-encoded by the C# tests. A staleness check fails when
     the C++ codec's output for them changes.
   - **Changes.** The protocol still changes only through a Spec and an ADR
     superseding ADR-0106. Its version string stays the gate.
3. **Generated C#** (Q2).
   - **Generator:** a second backend in the same pure generator,
     `generateCSharpBindings()`, selected by `atlantis_sdk_codegen --lang
     csharp`. C++ remains the default; its command and output are
     unchanged.
   - **Committed outputs:**
     - `src/csharp/Atlantis.Gameplay/Generated/World.g.cs`;
     - a synthetic test file.

     Both are deterministic, LF, `.gitattributes` `*.g.cs text eol=lf`,
     checked byte for byte by the C++ generator tests, with `.expected` on
     a mismatch. No .NET is needed to know they are current.
   - **Type mapping:**
     - `UInt64` → `ulong`;
     - `Float32` → `float`;
     - `Vec3Float32` / `Vec4Float32` → `System.Numerics.Vector3` /
       `Vector4`;
     - `AssetGuid` / `EntityGuid` → distinct `readonly record struct`s over
       `System.Guid`, used through text only;
     - enum → `enum X : long` with the constants' exact values;
     - struct → `public record struct`, nested as in the schema;
     - Optional → `T?`;
     - a non-Editable leaf → a read-only handle type.
   - **Names:**
     - types keep their schema names;
     - fields are PascalCased;
     - handles mirror the canonical path (`Fields.Light.Intensity`,
       `Fields.Camera.Fog.Density`);
     - a collision, C# keyword or generator-reserved name fails
       generation (ADR-0111 D5 extended).
   - **Value initialization** is C#'s default: zeros, `null`, enum value 0.
     Spec 0057 R10's contract carries over.
4. **Module** (Q4, M-a).
   - **A new top-level module, Atlantis C# SDK:**
     - `src/csharp/Atlantis.Gameplay/`, one class library, namespace
       `Atlantis.Gameplay`;
     - generated types in `Atlantis.Gameplay.World`;
     - the example in `examples/csharp/GameplayDemo/`, tests in
       `tests/csharp/`.
   - **Its rule:**
     - managed only;
     - coupled to the engine only through `atlantis.remote/1` and the
       generated bindings;
     - no native code;
     - .NET 10, zero NuGet (ADR-0113).
   - **Docs.** AGENTS.md lists it, noting it is not a C++ module and not in
     the native dependency graph.
5. **API and threading** (Q5).
   - **The typed surface** follows the C++ SDK:
     - `Get<T>(entity)` (one pipelined batch);
     - `Get` / `Set` by field handle;
     - `EntitiesWith<T…>()`;
     - a `Transaction` builder resolved whole at submit (`Add(entity, T)`
       only for all-Editable types);
     - `Subscribe` (`IDisposable`);
     - `FailureLog`;
     - `Decode`;
     - reflective overloads by path and id;
     - `Control` (pause, resume, step, status).
   - **Schema compatibility** is checked per type, recursively, as in
     Spec 0057 R5.
   - **Errors.** Connection, name and schema-mismatch errors are
     exceptions. World refusals of commands remain values, by ticket.
   - **Synchronous calls,** each blocking until its frame-boundary answer.
     A client object is not thread-safe. The client's process and
     threading are its own: ADR-0004 governs the engine's frame thread, not
     client processes. Async is named for later.
6. **Hot path: named only.** v1 crosses IPC and JSON on every call. A
   binary protocol, generated marshaling, shared memory or in-process
   hosting are future Specs, and nothing here presumes their shape.

## Consequences

### Positive

- C# gameplay code is typed from the one schema with no engine change. The
  engine, its frame, its goldens and the C++ SDK are untouched.
- No native ABI, no native DLL distribution, and no crash domain shared
  with native code: one managed assembly.
- The protocol gains a reference document and conformance vectors, which
  the next language (Python, 0061) needs anyway.
- Pipelining is native to the client that owns the socket.

### Negative / Trade-offs

- **A second codec and reflective layer** to keep in step with the C++
  ones (about 990 lines of codec and 1,160 of SDK on the C++ side today).
  The vectors and the live-server tests are the guard.
- **The hot-path principle is not met in v1.** Each call waits for a frame
  boundary.
- **The protocol becomes harder to change.** That is intended, but every
  change now touches two implementations and the reference.
- **PascalCase renaming** means C# names differ from schema and C++ names;
  paths in errors and documents use the schema's names.

## Alternatives Considered

- **P/Invoke over the native SDK (Q1 b).** Rejected for v1:
  - a C ABI over every SDK operation, value, variant, span and callback;
  - a native DLL per configuration and architecture;
  - marshaling stubs, which are a second generator target anyway;
  - a shared crash domain.

  All of this buys no latency, since it is the same IPC, and a hot-path v2
  would reshape that ABI.
- **In-process managed hosting (Q1 c).** Excluded by Spec 0057 and the
  maintainer.
- **CamelCase C# names.** Rejected as unidiomatic.
- **Own `Float3`/`Float4` types.** Rejected as foreign to C# gameplay code;
  the in-box `System.Numerics` types are plain floats.
- **Build-time C# source generators.** Rejected: they cannot be
  staleness-checked without .NET, and they break ADR-0111's
  committed-and-reviewed rule.
- **Async-only API.** Deferred: the protocol serializes per connection,
  and v1's loop is sequential.
