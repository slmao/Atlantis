## Context

- **E1/E2's models are C++** (`src/editor/include/atlantis/editor/model/`): the camera, picking and markers, the Gizmo,
  the hierarchy, the inspector, the edit target and the history. Atlantis Editor App is C# and may not link them
  (ADR-0125 D1).
- **One precedent exists.** The editor app's orbit camera is a C# port held to `camera_vectors.jsonl`, which a C++
  conformance test generates from `viewport_camera.h`. The test fails when the committed file is stale and writes
  the expected text for a reviewed copy; nothing rewrites it automatically.
- **Not every piece of the E3 editor has a C++ reference:**
  - the tree Hierarchy (E1's hierarchy is flat, over the World);
  - the structural records (ADR-0136);
  - the two-document flow (ADR-0135);
  - the authoring Inspector (E2's inspector reads the World's schema).
- **E1's Gizmo hit-testing is in the ImGui view** (`editor_view.cpp`: handle layout, pick distance, pointer-to-amount
  mapping), not in the model. No C++ test can call it as it stands.

## Decision

1. **Where a C++ reference exists, the C# port is held to it by vectors.**
   - A C++ test computes outputs from the C++ code over a fixed set of inputs. It commits them as JSON lines under
     `tests/csharp/conformance/`, and fails when the committed file differs from what the code computes now (the
     existing `checkCurrent` mechanism: an `.expected` file is written for a reviewed copy).
   - The C# test runner checks the C# port against every line within a stated tolerance.
   - Covered: the camera (all of `viewport_camera.h`), picking and markers (`viewport_picking.h`), the Gizmo's math
     (`gizmo.h`: decompose, compose, snapping, axes, drag), its handle layout, hit-test and pointer mapping (D3), the
     world-matrix solve over a node hierarchy (`world::World::updateTransforms()` / `getWorldMatrix()`, which the
     bake copies bit for bit), and the property history's semantics as transcripts
     (scripted operations against a fake target and the results they give).
2. **Where none exists, the ADR that specifies the behaviour is the reference,** and the C# tests check it, against
   fakes and the live Runtime. This applies to the tree, the structural records, the two-document flow and the
   authoring Inspector. No C++ copy is written only to generate vectors.
3. **E1's Gizmo handle math moves from the ImGui view into `gizmo.h` as pure functions,** behaviour-preserving, so
   that a C++ test can call it.
   - The functions are the handle layout from a camera and a matrix, the hit-test, and the pointer-to-amount
     mapping.
   - The frozen ImGui view calls them, and its E1 tests stay unchanged and green.
   - This is the one C++ editor change the E3 editor needs. It is a change that a shared-surface Spec requires
     under ADR-0125 D4 (the frozen editor's models are the reference the port keeps), not a thaw of the ImGui
     editor: no behaviour of it changes. A C++ test-only copy of the math was weighed and rejected (Plan 0068 J2,
     ruled 2026-10-27).
4. **A change to a C++ model that changes its vectors** is a change to the C# port as well, in the same PR. The
   stale-file failure enforces it.

## Consequences

### Positive

- **The C# editor and the frozen ImGui editor cannot drift apart unseen** on the math they share: camera, picking,
  Gizmo and history semantics.
- **No native code in the editor;** the vectors are plain data reviewed like code.
- **New behaviour is specified once,** in its ADR, and is not duplicated in C++ only to produce test data.

### Negative / Trade-offs

- **Vector files grow,** and every C++ model change regenerates them with review.
- **Behaviour without a C++ reference rests on C# tests alone.**
- **D3 touches the frozen ImGui editor's source** (behaviour-preserving, held by E1's unchanged tests).

## Alternatives Considered

- **A C# implementation with C# tests only:** nothing guards it against E1/E2.
- **P/Invoke into the C++ models:** a native dependency in the editor, against ADR-0125 D1.
- **C++ reference implementations for everything** (tree, structural records): a second implementation written only
  to generate data.
